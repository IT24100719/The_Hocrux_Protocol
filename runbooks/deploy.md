# Deploy on another computer

The whole CTF is reproducible from source, so moving it to a new host is: get the
files there, set secrets, build, seed. ~10 minutes on a prepared host.

---

## 1. Prerequisites on the new host
- **Docker Engine 27+** and **Docker Compose v2** (`docker compose version`) — that's all.
- Python is **not** required on the host: the bundled `seeder` container generates
  the artefacts and provisions CTFd. (Install `pyyaml pillow piexif scapy reportlab`
  only if you want to run `build-all.sh` / `tools/*.py` directly on the host.)
- (Optional) **VirtualBox 7 + Vagrant** — only if you run HX-06 as the lab VM
  instead of the bundled container.
- A Linux/macOS host is simplest. On Windows, use WSL2 or Git Bash so the `.sh`
  scripts run (and keep them LF — see note at the bottom).

---

## 2. Get the files onto the host

**These are gitignored, so `git clone` will NOT bring them — copy them by hand:**

| File / dir | Needed? | Why |
|---|---|---|
| `integration.yml` | **required** | single source of truth (flags, handovers); build-all and the seeder read it |
| `answer-key/` | optional | private solutions |
| `.env` | **do not copy** | create fresh on the new host with new secrets (step 3) |
| `challenges/**/dist/` | skip | regenerated by `build-all.sh` |

So either:
- **Clone the repo**, then copy `integration.yml` (and `answer-key/`) across separately; or
- **Copy the entire `horcrux-ctf/` folder** (tar/scp/USB) — simplest; everything comes, then still do a fresh `.env` (step 3).

---

## 3. Configure `.env`

    cp .env.example .env

Edit `.env` and set **new** values for this host:
- `LAB_IP` — see step 5 (127.0.0.1 for a single box; the host's LAN IP for a lab network)
- `DB_PASSWORD`, `CTFD_SECRET_KEY` — fresh strong random values
- `CTFD_ADMIN_NAME` / `CTFD_ADMIN_EMAIL` / `CTFD_ADMIN_PASSWORD` — the admin account the seeder creates
- `HORCRUX_START_POINTS` — welcome points (default 100)

You do **not** need to set `HX02_FLAG` / `HX02_CIPHERTEXT` by hand — `build-all.sh`
injects both from `integration.yml` in the next step.

---

## 4. Build and deploy — one command

    ./start.sh          # Linux / macOS / Git-Bash
    # Windows native:   powershell -ExecutionPolicy Bypass -File start.ps1

`start.sh` brings the stack up **and opens the CTF in your browser**, which lands
on the dark provisioning loading screen and auto-advances to CTFd when the seeder
finishes. (A container can't open the host browser, so this host-side wrapper
does it.) Prefer no browser / headless server? Just:

    docker compose up -d --build

Either way the stack starts, then the one-shot `seeder` container generates the
artefacts, publishes the HX-02 ciphertext/flag to a shared volume, waits for CTFd,
and provisions everything (challenges, flags, attachments, the unlock-in-order
prerequisite chain, 18 chained hints, the theme/story layer, the briefing page,
and the test user). Watch it finish:

    docker compose logs -f seeder         # wait for "the CTF is provisioned"

It re-runs idempotently on every `up` (generation is skipped once `dist/` exists)
and authenticates from `.env`, so no token is ever needed.

> Prefer to drive it from the host instead of the seeder container? The manual
> path still works: `./build-all.sh && docker compose up -d --build && python
> tools/seed_ctfd.py --test-user`.

---

## 5. Access it (single box vs lab network)
- **Single machine / local only:** `LAB_IP=127.0.0.1`. Reach CTFd at
  `http://127.0.0.1:8000/`.
- **Participants on other machines (lab LAN):** set `LAB_IP` to the host's LAN
  address (e.g. `192.168.56.10`), then `docker compose up -d` again. Published
  ports bind to that interface only — CTFd on `LAB_IP:8000`, HX-06 SSH on
  `LAB_IP:2222`. Never use `0.0.0.0`; keep the host off the public internet.

Players reach: CTFd `http://LAB_IP:8000/`, HX-02 at `/chamber`, HX-06 via
`ssh vault@LAB_IP -p 2222`.

---

## 6. Verify the deployment

    curl -I http://$LAB_IP:8000/           # CTFd responds
    for s in challenges/*/dist/SHA256SUMS challenges/*/dist/*.sha256; do \
      (cd "$(dirname "$s")" && sha256sum -c "$(basename "$s")"); done   # artefacts intact
    # HX-02 live:
    curl -s -c /tmp/cj -b /tmp/cj --data-urlencode "username=triddle'--" \
      --data-urlencode "password=x" -L http://$LAB_IP:8000/chamber/login | grep -o "Diary of T. Riddle"

Then solve HX-01 → HX-06 from a fresh account to confirm end to end.

---

## 7. HX-06: container (default) vs real VM
- **Container (default):** nothing to do — `docker compose up` builds and runs it,
  SSH on `LAB_IP:2222`.
- **Real lab VM at 10.10.20.60:** instead of the container, run
  `(cd challenges/hx06-vault && vagrant up)` on a host with VirtualBox, on a
  host-only/internal network. Same `provision.sh`, so the solve path is identical.

---

## 8. Moving an existing instance WITH player progress

The steps above give a clean CTF. To carry over player accounts, solves and scores:

    # on the OLD host:
    tools/backup.sh                        # -> backups/horcrux-<ts>.tgz
    # copy that .tgz to the new host, deploy clean (steps 1-4), then:
    tools/restore.sh backups/horcrux-<ts>.tgz

---

## 9. Teardown

    docker compose down                    # stop (keep data)
    docker compose down -v                 # stop + wipe the database and volumes

---

> **Windows note:** the shell scripts and `challenges/hx06-vault/provision.sh`
> must keep **LF** line endings. If you copy via Windows and git `autocrlf`
> rewrites them, convert back (`sed -i 's/\r$//' build-all.sh tools/*.sh
> challenges/hx06-vault/*.sh`) or the container build / scripts will fail.
